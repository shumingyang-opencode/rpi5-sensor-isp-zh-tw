4.2 控制資料流（完整追蹤）

你設 ExposureTime=20000→libcamera 轉換成感測器曝光行數→ov5647.c 寫 0x3500…→ISP 統計回饋→IPA 調整下一幀

你操作高階控制；libcamera 做「控制 → register」的轉換。理解這層抽象，tuning 檔才看得懂（單元 14）。

  • unicam 是 RPi 的 CSI-2 前端驅動，收集 MIPI 資料流。

4.4 DT overlay：每個欄位對驅動的意義

ov5647 overlay（概念，欄位意義）
compatible = "ovti,ov5647";     # 匹配 of_device_id → 載入驅動
reg = <0x36>;                    # probe 用 I2C 位址
clocks = <&cam0_clk>;              # XCLK 來源（pixel clock）
reset-gpios = <...>;             # RESET（CAM_GPIO）
pwdn-gpios = <...>;              # PWDN（如有）
port { csi-lane = <2>; }          # MIPI lane 數
欄位驅動用途
compatible與 of_device_id 匹配 → probe
regprobe 時 i2c_new_client_device 使用的位址
clocks供給 XCLK
reset-gpiosprobe 時先 reset（時序）
確認 overlay 生效
sudo dtoverlay -a | grep ov56
dmesg | grep -i -E "ov5647|unicam"

4.5 最小驗收

libcamera 看到相機
rpicam-hello --list-cameras
# 預期：ov5647，含 modes（2592x1944 10-bit …）
通過標準：list-cameras 出現 ov5647。沒出現 → 回單元 1（硬體）/ 6（決策樹）檢查。

4.6 常見錯誤

  • overlay 名與驅動不符：dtoverlay=ov5647 是 RPi 命名；驅動名是 ov5647.c。
  • 改 overlay 沒重啟：device tree 在開機時載入，改後需 reboot。
  • reg 位址與硬體不符：overlay 宣告 0x36，但板子實體位址不同 → probe 失敗。

4.6 深入：libcamera 的 Sensor 驅動介面

libcamera 對感測器驅動有一套「標準控制介面」，ov5647.c 實作：

libcamera 控制驅動如何滿足
ExposureTime寫 0x3500–0x3503（依行數換算）
AnalogueGain寫 0x350A–0x350B（查 gain map）
ColourGains寫 AWB gains register
VBlank/HBlank寫 timing register（影響幀率）
關鍵領悟：你設「ExposureTime=20000µs」，驅動負責把它變成「正確的 register 值」。讀懂這層轉換，就是從「會用」到「懂」的分水嶺。

4.7 深入：DT overlay 與內核匹配的完整鏈

dtoverlay=ov5647→firmware 併入 DTB→core 掃描 compatible→of_device_id 匹配 ov5647.c→probe→media 節點建立

compatible 寫錯一個字 → 驅動不 probe。這是「list-cameras 空」的常見根因。

4.8 練習

  1. 執行 dmesg | grep -i ov5647，找 probe 結果。
  2. 執行 rpicam-hello --list-cameras，記錄輸出的 modes。
  3. 把 DT 宣告的 I2C 位址與 i2cdetect 結果對照。

進階真實情境 Worked Example：用 media-ctl 追蹤完整管線並驗證格式一致

場景：你換了 OV5647 的 init table，但預覽畫面出現異常的綠色條紋。需要確認是 media 管線格式不一致還是 ISP 參數問題。

media 管線格式驗證
# 1. 完整列出所有 entity 與 pad format
media-ctl -p -d /dev/media0

# 輸出節錄：
# - entity 3: ov5647 0-0036 (1 pad, 1 link)
#     pad0: Source [fmt:SGBRG10_1X10/2592x1944]
# - entity 6: unicam (2 pads, 1 link)
#     pad0: Sink [fmt:SGBRG10_1X10/2592x1944]

# 2. 檢查 ISP pipeline handler 的格式轉換
media-ctl -p -d /dev/media0 | grep -A5 "rpi"

# 3. 若格式不一致，手動設定（不建議但除錯用）
# media-ctl -d /dev/media0 \
#   --set-v4l2 "ov5647 0-0036:0[fmt:SGBRG10_1X10/2592x1944]"

# 4. 用 v4l2-ctl 確認 streaming 格式
v4l2-ctl -d /dev/video0 --list-formats-ext
為什麼選這條路徑：media-ctl 是 V4L2 media framework 的除錯工具，能直接顯示管線上每個 entity 的輸入/輸出格式。若 source（感測器）輸出 SGBRG10_1X10 但 sink（unicam）期望 SRGGB10，就會導致色彩偏移。這個方法比「猜」快得多——直接看格式是否匹配，30 秒內定位問題。

深入原理擴充：libcamera pipeline handler 的自動格式推導機制

libcamera 的 pipeline handler（RPi 的 PipelineHandlerPiSP）在 probe 時自動建立 media graph，但它的格式推導邏輯比你想的複雜：

  • 感測器端：ov5647.c 的 init table 宣告支援的 format（SRGGB10、YUV420 等），pipeline handler 從中選擇「最佳」格式。
  • ISP 端：PiSP（RPi5 的 ISP）有硬體限制——某些 format 不支援直接輸入，需要額外的轉換 entity。
  • tuning 檔關聯：tuning 檔的格式必須與 pipeline 的實際 format 匹配，否則 ISP 會用錯誤的參數處理——症状通常是色彩偏差而非完全無畫面。
大家以為沒問題但其實是陷阱：很多人以為「compatible 寫對了就能用」，但 DT overlay 裡的 port { csi-lane = <2>; } 若寫成 csi-lane = <4>，驅動照樣 probe 成功（因為 lane 數是在 MIPI 層檢查的），但 streaming 時 unicam 會因 lane 數不匹配而靜默失敗——dmesg 可能不會出現明顯錯誤，只會「沒有畫面」。

進階挑戰題

  1. 用 media-ctl -p 畫出從感測器到 ISP 輸出的完整 entity 連結圖（用 ASCII 或文字描述），標出每個 link 的格式與方向（source→sink）。
  2. 設計一個「overlay 健康檢查」腳本：自動比對 DT overlay 宣告的 I2C 位址、lane 數、reset-gpios 與 i2cdetect / media-ctl 的實際結果，找出不匹配項。
  3. 若你想在 RPi5 上同時使用 OV5647（Camera 0）和自訂感測器（Camera 1），需要為 Camera 1 寫一份 DT overlay。描述你會如何確定 compatible、reg、clocks、reset-gpios 的值。

專案級端到端 Worked Example：自訂 DT overlay 接入第二顆感測器

場景：RPi5 的 Camera 1 要接一顆客製板上的 OV5647。官方 overlay 只覆蓋 Camera 0，你必須為 Camera 1 寫一份自訂 overlay，並驗證到 libcamera 看到兩顆相機。本專案整合單元 1（腳位）、3（I2C）、4（overlay/驅動）、6（bring-up）知識。

dtoverlay 檔：ov5647-cam1 的 dts 概念
// ov5647-cam1.dts（概念，欄位意義對應單元 4.4）
/dts-v1/;
/plugin/;
&i2c_csi_dsi1 {                       # Camera 1 的 I2C（i2c-10）
    compatible = "ovti,ov5647";        # 匹配 ov5647.c
    reg = <0x36>;                       # I2C 位址
    clocks = <&cam1_clk>;               # XCLK
    reset-gpios = <...>;               # CAM_GPIO 1
    pwdn-gpios = <...>;
    port { endpoint { data-lanes = <1 2>; }; };  # 2-lane
};
編譯、套用、驗證
# 1. 編譯 dts → dtbo（樹莓派工具鏈）
dtc -@ -I dts -O dtb -o ov5647-cam1.dtbo ov5647-cam1.dts
sudo cp ov5647-cam1.dtbo /boot/firmware/overlays/

# 2. 加入 config.txt 並重啟
echo "dtoverlay=ov5647-cam1" | sudo tee -a /boot/firmware/config.txt
sudo reboot

# 3. 驗證 probe（預期出現兩顆）
dmesg | grep -i ov5647
sudo i2cdetect -y 10 | grep 36        # Camera 1 的 bus
rpicam-hello --list-cameras
# 預期：0 : ov5647  1 : ov5647

# 4. 驗證 media graph 兩條管線
media-ctl -p -d /dev/media0 | grep -E "entity|ov5647|unicam"
專案規模與跨單元整合：自訂 overlay 是「客製板接入」的核心技能：compatible 對應驅動匹配（單元 4）、reg 對應 I2C（單元 3）、clocks/reset 對應上電時序（單元 6）、data-lanes 對應 MIPI lane 一致性（單元 6.3）。驗證到 list-cameras 出現兩顆 + media graph 兩條管線，就是專案完成標準。

量測/驗證 SOP：驅動載入與 media graph 驗證

  1. dmesg | grep -i ov5647 確認兩顆都 probe（含 Chip ID）。
  2. sudo i2cdetect -y 10（Camera 1）與 -y 22（Camera 0）確認各自 0x36。
  3. rpicam-hello --list-cameras 確認兩顆 camera 索引。
  4. media-ctl -p -d /dev/media0（與 media1）比對感測器 pad 格式與 unicam sink 格式一致。
  5. 雙鏡頭各拍一張 RAW，確認無格式錯誤。
  6. 記錄 media graph 輸出存檔。
判讀指標：source 與 sink 格式不一致（如 SGBRG10 vs SRGGB10）→ 色彩錯亂；只有一顆 probe → 檢查該 Camera 的 bus/overlay；list-cameras 空 → 回單元 1 硬體層。

② 多層疑難排解決策樹

決策樹 A：libcamera 與 V4L2 工具衝突

工具衝突
├─ 檢查 A：cam -d /dev/media0 是否佔用 pipeline
│  ├─ 是 → 關閉 cam 後再用 v4l2-ctl
│  └─ 否 → 繼續
├─ 檢查 B：rpicam-hello 是否在背景執行
│  ├─ 是 → kill 後重試
│  └─ 否 → 繼續
└─ 檢查 C：是否有其他 process 打開 /dev/video*
   ├─ 是 → lsof /dev/video* 找出並終止
   └─ 否 → driver 問題，檢查 media topology

③ 量測驗證完整 SOP：Pipeline 延遲量測

  1. 方法：GPIO 觸發 + 影像時間戳比對
  2. 硬體：RPi5 GPIO 17 接 LED + 示波器
  3. 軟體：在影像 callback 中拉 GPIO High，從 raw frame header 讀取 timestamp
  4. 量測：
    a. GPIO rising → frame timestamp = sensor → ISP 延遲
    b. frame timestamp → callback timestamp = ISP → 應用延遲
    c. 總延遲 = a + b
  5. 重複：100 幀取 p50 / p99 / p99.9 latency
  6. 判讀：p50 <33ms (30fps), p99 <50ms = 正常；jitter >10ms = pipeline 有 blocking
